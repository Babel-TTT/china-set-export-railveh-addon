# 出口铁路载具制作工作台

一个**本地运行**的可视化工作台，把本工程的操作链路（数据表 → 单车 PNML → 体素模型 →
精灵图 → GRF）搬到浏览器里。参考并沿用 `openttd-newgrf-builder` 的
`web/workbench` 结构：纯 Python 标准库的 HTTP 服务 + 原生 JavaScript 前端，
不需要 npm、不需要打包步骤。

## 启动

```bash
python3 web/workbench/server.py
# 或
make workbench
```

然后打开 <http://127.0.0.1:4174/workbench/>。

只监听回环地址，面向单人制作与审核，不提供多用户权限或远程部署能力。

## 设计原则

**工作台不重新实现任何生成逻辑。** 服务器只做三件事：

1. 读 `data/*.csv`；
2. 看 `src/` 与 `gfx/` 里的文件状态；
3. 用 `subprocess` 调用仓库里已有的工具。

所有真实工作仍由这些命令完成：

| 命令 | 作用 |
| ---- | ---- |
| `genpnml.py --strings` | 刷新 `docs/str.csv` |
| `genpnml.py --data data --out src` | 写每台车的 `.pnml`，并补齐每个 `gfx/<目录>/` 的 `manifest.json` 与 `ttd_palette.json` |
| `genpnml.py --check` | 字符串表双向核对 |
| `tools/verify_assets.py` | 贴图引用与渲染结果核对 |
| `make sprites` | `renderobject` 渲染 8 方向精灵图 |
| `make` | 预处理 + `nmlc` 编译出 `.grf` |

界面里的每个表单字段都来自 `schema.py`，所以给数据表加一列时**只需要改
`schema.py`**，前端会自动出现对应控件。

## 八个阶段

| 阶段 | 内容 |
| ---- | ---- |
| 1 车队总览 | 四张表的汇总，**按购买菜单顺序**排列，显示 ID 段分配、涂装数量、轨距标签、贴图是否就绪；每张卡可直接改购买菜单的分组、顺序与折叠项名称；可搜索、按表筛选 |
| 2 车辆工作台 | **同一页三层**：车辆属性 → 涂装管理 → 分节图像（详见下节） |
| 3 货运外观 | `cargo_variants.csv`，附开关链路示意 |
| 4 字符串表 | `docs/str.csv` 的常量、英文、中文；按「涂装 / 车辆名 / 界面」分类筛选，可新增、改名、删除 |
| 5 一致性检查 | 字符串表与贴图引用检查，输出滚动显示 |
| 6 构建 GRF | `make` 的完整日志与产物体积 |
| 7 指南 | 离线浏览仓库内的中文文档 |

左栏的「确定性操作」与各阶段的按钮都走同一条作业通道：任务在后台线程里跑，
前端轮询增量日志，因此长编译不会让页面卡住。

## 车队总览：购买菜单的分组与排序

第 1 阶段的车队总览**按购买菜单顺序**排列，每张卡片上带购买菜单三列
（`variant_group`、`menu_order`、`series_string`）的控件：

| 控件 | 作用 |
| ---- | ---- |
| `顺序 N / M` + `▲` `▼` | 在购买菜单里上移 / 下移一位。箭头移动的是**整份购买菜单里的位置**，不是屏幕上筛出来的那一份，所以搜索或按表筛选不会改变它的含义；每次移动都把整份名单的 `menu_order` 按 10 递重重排（10、20、30…），以后想插到两行之间还有空位 |
| `折叠到` 下拉框 | 这台车折叠到哪台车下面。候选只列**同一张表**里、不是它自己、也不是它后代的那些车（否则会成环）；「独立一条」= 清空这一列 |
| `折叠项名称` 输入框 | 折叠行显示的 `STR_` 常量；常量不在字符串表里时旁边标红「字符串不存在」 |

卡片上的提示标签：「N 个变体折在这里」= 有别的车折在它下面；「自己也折叠了」= 这台车
自己也折在别人下面，也就是生成器对**嵌套**给出的那条警告（上游把嵌套标为实验性）。

三列都通过 `POST /api/fleet-menu` 保存，请求体形如
`{"rows":[{"table","id","variant_group","menu_order","series_string"}]}`：
**没带的键保持原样**（拖顺序不必重发分组，改分组不必重发顺序），**带了不认识的键会被
拒绝**，而且改到的每张表**先全部校验通过才落盘**——分组规则用的就是生成器自己的
`genpnml.check_variant_groups()`，与 `make` 编译时是同一条。保存后还要跑一次
「生成车辆代码」（或 `make gen`），`src/vehiclesort.pnml` 与名字回调才会跟上。

## 车辆工作台：三层递进

「车辆工作台」把原来分散在三个阶段里的东西按依赖顺序放在同一页，因为它们是
**同一件事的三个层次**，而不是三件并列的事：

| 层 | 管什么 | 写在哪 |
| -- | ------ | ------ |
| **1 车辆属性** | 这台车是什么：id、类别、`parts` 分段、车身段（`power_section`）、寿命、性能…… | 四张车辆表之一 |
| **2 涂装管理** | 这台车有哪几种涂装，每种用哪个 `.vox`，以及它自己的分节换图规则 | `liveries.csv` |
| **3 分节图像一览** | 选中的那种涂装，每段在什么条件下显示哪张图：规则按**开关树**缩进显示，一层开关一行（只读，规则在第 2 层编辑） | `liveries.csv` 的 `graphics_parts` |

三层的衔接规则：

- 第 2 层的每一行都显示它解析出来的**模型文件名**
  `gfx/<folder>/<id>[-<后缀>].vox` 以及该文件的三个状态（缺 `.vox` / 未渲染 / 已渲染），
  所以「后缀」不再是一个需要心算的字符串。
- 本车**第一行**涂装另外显示一张**菜单图**：车库购买列表里那台车的小图取的就是它
  （生成物里的 `graphics { purchase: … }`），带自己的「已渲染 / 缺这张图」标记。
  默认与「模型」相同；`purchase_suffix` 可以让它借用另一张已经画好的图——
  本行自己的模型还没画时，这是让构建先通过的办法（见 `data/README.md` 的 `liveries.csv`）。
- 分节换图规则**属于涂装**：同一台车的每个涂装各有一套，编辑框就在第 2 层的那一行里。
  它有两种编辑方式，两种都走生成器自己的解析器，所以都不会与 `make gen` 各说各话：
  - **图形化的开关块（默认）**：每一段有三种模式——「隐形」（`empty_sprites`）、
    「一张图」（直接一个精灵集）、「按条件分」（一个 `switch`）。开关块里，块头的
    变量下拉就是 `switch` 的选择器，每一行就是一个 `case`：运算符下拉里只有
    `<=`、`==`、`>=` 和「区间」四种，都是单元格能**原样存回**的写法——`<` 与 `>`
    是 `<=` / `>=` 的同义词（数字差一位），生成器写回时就换成后者，列出来只会显得
    「选了又跳回别的符号」；选「区间」时是两个数字框、中间一个 `..`，对应
    `3..8` 这样一个 case（`0..6` 就是 `<=6`、会写回成 `<=`，所以选中「区间」时
    控件先把两头摊成真正的区间）。目标可以是**一个模型**（`return spriteset…`）
    或者**「再筛一层」**（`return switch…`，也就是嵌套开关）；最外层开关的「其余」
    还能选「再筛一层」，那就是串联的下一层开关。
    界面上的控件与生成的 NML 一一对应，见指南 §7.7 的对照表。
  - **直接编辑文本**：展开「直接编辑文本」按 NML 语法手写整格。
  两个视图互相刷新，输入按 **250 ms 防抖**。
- 编辑器的每次操作都把整棵树 `POST /api/graphics-parts` 给服务器，由 `genpnml.py`
  写回单元格**再解析一遍**，界面显示的就是编译时会读到的那一格值：所以工作台做不出
  生成器不接受的规则，表格语言表达不了的形状（例如嵌套开关自己再当默认）会直接报出原因。
  报出来的就是生成器那条具体的拒绝理由（哪一段、哪条规则、错在哪），例如
  `第 2 段的 'pos<0=a' 无法解析：条件 'pos<0' 永远不成立`；只有基名写错时才是那句
  通用的「基名只能用小写字母、数字、下划线和连字符」（基名就是贴图基名，
  `df4c-korea-1`、`tm2-a` 这类带连字符的名字可以直接选）。
- **写回失败就不让保存**：写回失败时，屏幕上那些开关块**不是**单元格里的内容，
  所以「保存这一行」会直接拒绝并说明原因，而不是把旧的单元格存下去——否则屏幕看着像
  存过了，实际改动全丢。
- 第 3 层把规则树**按缩进显示**，与编译出来的嵌套开关一一对应：一层开关占一行
  「按 `pos` 判断」（如果它是上一层某个区间里链出来的，前面还会带上「`consist 0..6`：」），
  它下面的每个分支各占一行并再缩进一级，叶子写成「`pos 0..2` → `基名`」，
  没有条件的兜底写成「其余情况 → `基名`」，空段写成「这一段隐形（用 `empty_sprites`）」。
- `server.py` 记住 `genpnml.py` 的修改时间，**文件一变就重新加载**它，所以改完生成器
  不需要重启服务器：编辑器校验的始终是磁盘上的那一份代码。
- 点第 2 层的「查看图像」，第 3 层就切成那一行的模型与规则；`liveries.csv` 的行序即改装菜单里的涂装序号，
  第 2 层的 `#0` 是自动项。
- 第 3 层列出规则引用到的每个基名及其文件状态，并高亮当前这一行的模型。

## 接口

| 方法 | 路径 | 作用 |
| ---- | ---- | ---- |
| GET | `/api/schema` | 列元数据、类别、ID 段、轨距标签、货物标签 |
| GET | `/api/state` | 车队、涂装、外观、ID 分配、贴图状态、字符串表、GRF 体积 |
| GET | `/api/strings` | `docs/str.csv` 的三列全文（含注释行） |
| GET | `/api/vehicle?table=&id=` | 一台车的完整数据行 |
| GET | `/api/pnml?table=&id=` | 该车已生成的 PNML 文本 |
| GET | `/api/rules?cell=&parts=` | 用生成器自己的解析器把一格 `graphics_parts` 解析成规则树（第 3 层的预览走这里，所以不会与生成的 NML 不一致） |
| POST | `/api/graphics-parts` | 把编辑器搭出来的开关树写回单元格并重新解析，返回规范化的 `cell` 与规则树（第 2 层的图形编辑器走这里） |
| GET | `/api/sheet?path=` | 精灵图里 8 个视图的精确裁剪框 |
| GET | `/api/file?path=` | 仓库内文件（预览 PNG / GRF） |
| GET | `/api/text?path=` | 仓库内文本（指南） |
| GET | `/api/job?job=&cursor=` | 增量读取作业输出 |
| POST | `/api/save` `/api/copy` `/api/delete` | 增删改数据行（涂装行按 `index` 定位） |
| POST | `/api/fleet-menu` | 批量改购买菜单的分组、顺序与折叠项名称：没带的键不动，改到的表先全部校验再落盘 |
| POST | `/api/move` | 涂装行上移 / 下移 |
| POST | `/api/string` `/api/string-delete` | 增删改 `docs/str.csv` 的一行 |
| POST | `/api/run` | 白名单动作：`gen` `vox` `render` `check` `build` `clean_gen` |

### 前端写的是「`/api` 之后的那一段」

`app.js` 里 `jsonFetch(path)` 自己会补上 `API = '/api'`，所以调用点写
`jsonFetch('/graphics-parts', …)` 而不是 `jsonFetch('/api/graphics-parts', …)`。后者会
请求 `/api/api/graphics-parts`：服务器只回一个 404，浏览器里既不报错也不提示，只是那个
按钮永远不生效——第 2 层的写回就这么挂过一次。

`tools/check_workbench_routes.py` 把 `app.js` 的每个调用点与 `server.py` 的路由表对一遍
（连 GET/POST 一起对），不启动服务器就能查：

    python3 tools/check_workbench_routes.py

它也是工作台「一致性检查」按钮的一步。第 2 层的编辑器还可以对着**运行中的**服务器跑一遍，
每一步都会把单元格交给生成器重新解析：

    node tools/check_rule_editor.js http://127.0.0.1:4174

### 涂装行为什么按行号定位

`liveries.csv` 的一行由四个**都可编辑**的单元格组成（`id`、`sprite_suffix`、
`from_year`、`to_year`），按整行匹配意味着改掉任意一个字段之后，这一行就再也
找不回来了——删除时会报「liveries.csv 中找不到该行」，而那一行明明在表里。
所以涂装行和车辆行一样**按表内序号定位**：浏览器把它渲染的那个 `_index` 一起发回来，
服务端优先按序号取行，只有在没有序号时才退回按键值匹配。

同一个 `id` 下解析出相同基名的两行是**错误**（生成器会重复声明同一个精灵集）；
年份区间重叠是**警告**——它编译得出来（nmlc 取行序靠前的那条 case），但通常不是本意。

## 字符串表

涂装名、车辆名和所有界面文字都来自 `docs/str.csv`。工作台把这张表做成可编辑列表：
常量、英文、中文，并标出每一行是否被引用。

表里混着三类文字，所以列表上方有分类按钮和搜索框：

| 分类 | 前缀 | 说明 |
| ---- | ---- | ---- |
| 涂装 `LV_` | `STR_LV_` | 涂装标签。`liveries.csv` 里写 `LV_EXPORT_BLUE`，代码里就是 `STR_LV_EXPORT_BLUE`，所以涂装标签自成一组，不用在上百条 `STR_` 里找 |
| 车辆名 | `STR_NAME_`、`STR_FULL_NAME_` | 生成器按车辆 id 造出来的名字 |
| 界面 | 其余 | 参数说明、菜单文字、描述模板 |

打开字符串表页时默认就停在「涂装 LV_」这一组。

- **新增的行会被保留**：`genpnml.render_strings()` 除了保留生成行的中文列，还会原样保留
  它不认识的整行。所以从工作台加一个 `LV_EXPORT_BLUE` 之后，`make gen` 不会把它删掉。
- 完全空的手写行（英文、中文都为空的占位）会被丢弃，避免表里堆积空行。
- 删除仍被引用的常量会让 `--check` 报 `MISSING`，所以那一行的标签会提醒你。

## 写入安全

工作台会直接修改编译源数据，因此有四道闸门：

1. **写前校验**（与 `genpnml.py` 同样的规则）：id 合规、表内不重名、`folder`
   是单层目录、`parts` 与 `power_section` 自洽、`track_type` 必须在
   `src/railtypetable.pnml` 里、涂装与外观的 `id` 必须指向真实存在的车，
   同车涂装不得共用同一个 `.vox`，分节图像规则的段数必须等于该车的 `parts` 段数、
   条件必须合法。校验失败时不写盘，错误逐条列在状态栏；
   不阻塞的年份重叠则作为警告显示并照常写入。
2. **原子写 + 备份**：先写临时文件再 `os.replace`，原文件留
   `<table>.workbench.bak`。
3. **路径围栏**：所有路径经 `repo_path()` 解析，拒绝逃出仓库。
4. **未知列不丢**：保存时以读到的原始行为基底做合并，将来给 CSV 加列不会被
   工作台抹掉。

## 关于精灵图裁剪

`renderobject` 输出的 `_32bpp.png` **不是等分网格**：8 个视图宽度不同
（36 / 120 / 192 px），每格后带 8 px 透明内边距，高度方向居中。服务器读取同目录的
`manifest.json` 与 PNG 头部尺寸算出每格的精确裁剪框，和 `src/template.pnml` 里
手写的坐标一致。前端如果按固定网格切图会把车切成两半，所以必须走 `/api/sheet`。
